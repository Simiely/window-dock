# Windows 窗口停靠 Dock：调研与方案

> 目标：一个常驻小工具，把程序/窗口放进一条侧栏 Dock，支持单个或成组快速调取，支持「框选成组 → 原位释放」。
> 本文只做调研与方案，不含实现代码。文中 API 名称、版本限制均按 Microsoft Learn 文档核对过。

---

## 0. 一句话结论

**值得做，但不要做成「又一个 macOS Dock 启动器」。**

现有产品里，`WindowTabs`（MIT、2026 年仍在维护）已经覆盖了「窗口分组 + 组内一起移动 + 保存/还原窗口位置」的 60%；`AquaSnap` 覆盖了「成组移动」；`PowerToys Workspaces` 覆盖了「按布局启动应用」。**没有任何一个产品同时提供「把任意窗口收进一条容器侧栏 + 矩形/套索框选成组 + 一键原位还原」。** 这就是差异化空间。

最小代价落地路径：**C# / .NET 8 + WPF（单 exe、托盘常驻、不注入进程、不提权）**，先做 4 件事：拖入/钉住 → 单窗口热键 → 矩形框选成组 → 原位还原。套索、跨虚拟桌面、持久化重启放到 P1/P2。

## 1. 需求拆解

把原意拆成能力单元，并标注「Win32 能不能做」的初判，作为后文的索引。

| # | 需求 | 本质能力 | 初判 | 备注 |
|---|------|----------|------|------|
| R1 | 常驻侧栏 Dock | 置顶、无边框、自动隐藏的独立窗口 | 可做 | 纯自家窗口，无系统限制 |
| R2 | 把其他程序拖进去 | OLE 拖放（.lnk/.exe）+「当前前台窗口」入库 | 可做（拖文件）；拖窗口需 hack | 任务栏拖拽不可行 |
| R3 | 多个程序/窗口 + 不同排列方案 | 数据模型 + 布局求解 | 可做 | 排序/分组是纯应用层逻辑 |
| R4 | 单窗口快捷键调取 | 全局热键 + 还原/激活 | 可做，但**前台激活受限** | 最大暗坑之一 |
| R5 | 成组一起放出 | 批量 SetWindowPos + 记录布局 | 可做 | 需要 DPI/显示器换算 |
| R6 | 抓取模式（矩形 + 套索） | 全屏透明覆盖层 + 命中判定 | 可做 | 套索只是判定算法差异 |
| R7 | 释放回原位 | 位置快照 + 边界处理 | 可做，但**边界情况多** | 窗口关闭/DPI 变化/拔屏 |
| R8 | 多显示器 / 混合 DPI | per-monitor v2 + 坐标换算 | 可做，易错 | 必须一开始就按物理像素建模 |

**关键设计判断**：不要把「停靠」实现成 `SetParent` 跨进程嵌入。跨进程 `SetParent` 会破坏目标窗口的消息循环、输入焦点、DPI 感知和 DWM 合成，Electron/Chromium 这类自绘应用几乎必崩。**「停靠」应定义为「由 Dock 负责摆放和记账的普通顶层窗口」**，Dock 只是控制器，不是容器。

## 2. 同类方案对比

### 2.1 对比表

| 方案 | 类型 | 覆盖 R1–R8 的情况 | 收费 | 稳定性/边界 | 可借鉴点 |
|------|------|-------------------|------|-------------|----------|
| **Windows 11 Snap Layouts / Snap Groups** | 系统内置 | 只有 R4/R5 的一部分：贴靠布局 + 系统自动生成 Snap 组，悬停任务栏图标可整组恢复 | 免费 | 很稳，但组是**系统自动生成**，不能自定义成员，不能跨虚拟桌面保留，窗口一移就散 | R5 的交互范式（任务栏悬停恢复整组）可直接抄 |
| **PowerToys FancyZones** | 布局工具 | 只覆盖「摆放」：把窗口拖进分区，不记录窗口身份，不成组，不还原 | 免费（PowerToys） | 稳定；靠全局鼠标/窗口事件钩子接管拖动，与自定义拖动逻辑会打架 | 分区布局编辑器的交互；默认热键 `Win+Shift+\`` |
| **PowerToys Workspaces** | 工作区 | 覆盖 R5 的一半：保存「应用 + 位置 + 参数」，一键启动到指定位置 | 免费 | 稳定；**只能启动应用，不能收纳已在运行的窗口** | 「工作区 = 启动配置 + 布局」的数据结构 |
| **WindowTabs** | 窗口分组（标签） | R2/R3/R5 的强参考：任意窗口成组、组内一起移动缩放、**Workspaces 保存组和窗口位置并还原到已打开窗口**，未运行的应用可启动后还原 | 免费、MIT 开源 | 活跃（v2026.11.05-beta）；F# WinForms/.NET Framework 4.8；官方明确说明「以管理员运行会破坏拖放」 | **最值得读源码的项目**：Win32 封装、DPI 缩放、组内联动、Workspaces 还原策略 |
| **Stardock Groupy 2** | 标签分组 | 覆盖 R3 的一部分（标签化），不含抓取/套索 | US$9.99 / €11.99（5 台设备） | 用户反馈 UWP、Electron（Chrome/Teams/WhatsApp）常有对齐/兼容问题，且会干扰 Win11 最大化按钮的 Snap Layouts 弹出 | 标签栏的视觉与「拖 tab 成组」交互 |
| **AquaSnap** | 窗口管理 | 覆盖「边缘停靠 + 吸附 + Move windows together（成组移动）」 | 个人免费 / Pro US$29 | 稳定，老牌；它的「docking」是吸到屏幕边缘，不是容器 | 成组移动的相对偏移算法 |
| **DisplayFusion Pro** | 多显示器管理 | 热键、窗口移动、多显示器任务栏 | Free / Pro US$34 起 | 稳定 | 多显示器与热键的工程化处理 |
| **MyDockFinder** | macOS 风格 Dock | 覆盖 R1/R2/R4 的表层：拖入图标、窗口预览、最小化到 Dock（D3D11 动画） | Steam 约 US$4–5.5（区域定价） | 商业闭源；模拟 Finder 菜单栏，系统升级后易出兼容问题 | Dock 的视觉、悬停预览、最小化动画 |
| **Dexpot** | 虚拟桌面 | 与 R5 无关，属于另一维度 | 免费 | 主版本长期停在 1.6.x，Win10/11 兼容需实测 | 虚拟桌面与窗口归属的判断思路 |
| **RocketDock / Winstep Nexus / ObjectDock** | Dock 启动器克隆 | 只有 R1，纯粹启动器，不收窗口 | 免费/付费混合 | RocketDock 早已停更 | 仅视觉参考 |

### 2.2 结论：哪些能抄，哪些没有现成解法

**能直接抄的经验**
1. **任务栏悬停恢复整组**（Snap Groups）：用户对「一个入口恢复一组窗口」已有肌肉记忆，交互不用教育。
2. **Workspaces 数据模型**（PowerToys / WindowTabs）：`应用标识 + 启动参数 + 目标矩形 + 显示器`，是持久化的最小充分信息。
3. **组内联动移动**（AquaSnap / WindowTabs）：保存相对偏移，移动时批量 `DeferWindowPos`，避免 N 次闪烁。
4. **Dock 视觉与悬停预览**（MyDockFinder）：分层窗口 + 图标放大 + DWM 缩略图（`DwmRegisterThumbnail`）。

**没有现成解法、必须自研的部分**
1. **把「任意窗口」变成 Dock 的成员并记账**：没有系统 API 提供「窗口容器」。系统虽然有 `Windows.UI.Shell.WindowTabGroup`（WinRT，桌面应用可用），但**只对主动调用它的应用生效，无法从外部把别人的窗口塞进组**。
2. **矩形/套索框选成组**：没有任何产品做这个。需要自绘覆盖层 + z-order 命中判定。
3. **「原位还原」的语义**：Snap Groups 只恢复「贴靠关系」，不保证像素级原位；Workspaces 是「启动到位置」而非「把现有窗口搬回去」。需要自己定义并处理边界。
4. **与系统贴靠/第三方分组器共存**：没有官方协调机制，只能靠「不改目标窗口样式、不模拟拖动」来降低冲突。

## 3. 机制可行性逐项

> 约定：下文「可做」指普通权限（非管理员）的桌面进程即可实现；标注「受限」的项在 MVP 中应降级或砍掉。

### 3.1 窗口枚举与识别

| 能力 | 结论 | 关键 API | 坑 |
|------|------|----------|-----|
| 枚举顶层窗口 | 可做 | `EnumWindows` + `IsWindowVisible` + `GetWindowRect` | 只枚举顶层；顺序即 z-order（从顶到底） |
| 过滤工具窗口/悬浮窗 | 可做 | `GetWindowLongPtr(GW_EXSTYLE)`，排除 `WS_EX_TOOLWINDOW`、`WS_EX_NOACTIVATE` | 输入法候选窗、托盘气泡、桌面 `Progman`/`WorkerW` 都要排除 |
| 识别「被隐藏但仍存在」的窗口 | 可做 | `DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED, ...)`（值 14） | 返回 `DWM_CLOAKED_SHELL`(0x2) 表示被 Shell 隐藏——**其他虚拟桌面的窗口就属于这类**；`DWM_CLOAKED_APP`(0x1) 常见于 UWP 挂起 |
| 识别 UWP/打包应用 | 可做，但要绕 | 顶层是 `ApplicationFrameWindow`（进程 `ApplicationFrameHost.exe`），真实内容在子窗口 `Windows.UI.Core.CoreWindow`；应用身份用 `SHGetPropertyStoreForWindow` 读 `PKEY_AppUserModel_ID` | 直接 `GetWindowThreadProcessId` 会拿到 `ApplicationFrameHost.exe`，**必须下钻子窗口取 PID**；同一 AUMID 可能有多个窗口 |
| 区分「程序」与「窗口实例」 | 可做（自定义模型） | `AppKey = exe 规范化路径 或 AUMID`；`InstanceKey = (HWND, PID, 进程启动时间)` | HWND 会被系统复用；标题会变；浏览器一个进程多窗口。**用 PID + 进程启动时间做二次校验**，不要只存 HWND |
| 最小化窗口 | 可做 | `IsIconic`；`GetWindowPlacement` 的 `rcNormalPosition` 是还原后的位置 | 最小化窗口的 `GetWindowRect` 常是 `-32000` 之类的哨兵值，**不能用它做位置快照** |
| 增量感知窗口变化 | 可做 | `SetWinEventHook`：`EVENT_OBJECT_CREATE/DESTROY/SHOW/HIDE`、`EVENT_SYSTEM_MINIMIZESTART/END`、`EVENT_SYSTEM_FOREGROUND`、`EVENT_OBJECT_LOCATIONCHANGE`，`WINEVENT_OUTOFCONTEXT \| WINEVENT_SKIPOWNPROCESS` | `LOCATIONCHANGE` 触发频率极高，必须节流（≥100ms 合并）；回调在非 UI 线程，需 `Dispatcher.BeginInvoke` |

### 3.2 「拖入」Dock

| 路径 | 结论 | 说明 |
|------|------|------|
| 从资源管理器/桌面拖 `.lnk` / `.exe` | **可做，推荐** | 标准 OLE 拖放：`RegisterDragDrop` + `IDropTarget`，格式 `CF_HDROP` 拿到路径。`.lnk` 用 `IShellLinkW::GetPath` 解析；WPF 的 `AllowDrop=true` 已封装这一层 |
| 从任务栏拖动窗口按钮 | **不可行** | 任务栏按钮不是 OLE 拖源，Windows 也没有「跨进程拖窗口」的公开接口。不要在这上面花时间 |
| 从窗口标题栏拖进 Dock | **技术可行但强烈不建议做 P0** | 需要全局 `WH_MOUSE_LL` 钩子判断「按住标题栏拖动 + 指针进入 Dock 热区」。代价：与 FancyZones/Groupy 的低级钩子叠加、提权窗口前台时行为不确定、误触会打断用户拖动。**替代方案：全局热键或 Dock 右键菜单「把当前前台窗口加入」**，一条 `GetForegroundWindow` 即可，可靠得多 |
| 以管理员身份运行时拖放 | **会失效** | UIPI 会阻断低完整性进程（普通 Explorer）向高完整性窗口（提权 Dock）的 OLE 拖放。WindowTabs 官方 README 明确记录了这一点。**默认不要提权** |

### 3.3 停靠、吸附、置顶

- **把窗口「停靠」到侧栏位置**：用 `SetWindowPos(hwnd, HWND_TOP, x, y, w, h, SWP_NOACTIVATE)` 逐窗摆放即可。**不要改目标窗口的扩展样式**（不加 `WS_EX_TOPMOST`、不加 `WS_EX_LAYERED`），否则会和 WindowTinter、Groupy 抢同一份窗口状态。
- **Dock 自身层级**：`WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`，配合 `ShowWindow(SW_SHOWNOACTIVATE)`。Win11 可用 `DwmSetWindowAttribute` 设置 `DWMWA_WINDOW_CORNER_PREFERENCE`（33）圆角、`DWMWA_SYSTEMBACKDROP_TYPE`（38）亚克力/云母（22H2+ 才有）。
- **Dock 移动后窗口跟随**：保存「窗口相对 Dock 锚点的偏移」，Dock 换边/换位时用 `BeginDeferWindowPos` / `DeferWindowPos` / `EndDeferWindowPos` 一次性提交，避免闪烁。
- **与 Windows 贴靠的冲突**：Aero Snap / Snap Layouts / FancyZones 都绑定在**用户拖动标题栏**这条路径上；**程序化 `SetWindowPos` 不会触发它们**。所以只要不模拟 `WM_NCLBUTTONDOWN + HTCAPTION` 拖动，就不会被系统重新吸附。反过来，用户**手动**拖组内窗口仍会被 FancyZones 吸走，这是产品说明里要写清楚的预期行为。
- **不要试图创建 Snap Group**：Snap Groups 由系统在贴靠时自动生成，没有公开 API 让第三方建组；能做的只是「把窗口摆成贴靠后的矩形」。

### 3.4 调取（单个 / 成组）

**单个窗口激活**是本项目最容易被低估的坑。`SetForegroundWindow` 有明确的前台锁限制，文档列出的放行条件包括：前台超时 `SPI_GETFOREGROUNDLOCKTIMEOUT` 已过期、调用进程是前台进程、由前台进程启动、当前没有前台窗口、调用进程收到最后一次输入、或任一方处于调试中；不满足时 Windows 只会**闪烁任务栏按钮**。

- 常规做法：`ShowWindow(hwnd, SW_RESTORE)` → `SetForegroundWindow(hwnd)`；失败则 `FlashWindowEx` 提示，或 `AttachThreadInput(前台线程, 本线程)` 后重试再分离（这是业界常用绕过法，但不是官方保证）。
- **不建议**修改 `SPI_SETFOREGROUNDLOCKTIMEOUT` 为 0：全局副作用，且需要注销/重启才生效，属于「用户环境破坏」。
- **跨虚拟桌面**：`IVirtualDesktopManager`（Win10+，`CoCreateInstance(CLSID_VirtualDesktopManager)`）只有三个方法：`IsWindowOnCurrentVirtualDesktop`、`GetWindowDesktopId`、`MoveWindowToDesktop(GUID)`。**没有公开 API 枚举桌面或取「当前桌面 GUID」**；想「切到窗口所在桌面」只能用未公开 COM（各 Windows build 接口不同，Win11 升级即坏）。→ **MVP 不做跨桌面切换**，只做「检测到不在当前桌面就提示」。
- **跨显示器**：`SetWindowPos` 用物理像素坐标；per-monitor v2 进程在跨 DPI 屏移动时会收到 `WM_DPICHANGED`，尺寸会被系统改动，需在下一帧重新校正。
- **成组放出**：一次 `DeferWindowPos` 提交所有矩形，最后再 `SetForegroundWindow` 组内主窗口。顺序很重要：先全部 `ShowWindow(SW_RESTORE)`，再统一摆放，最后激活，否则会出现窗口互相抢前台。
- **坑**：UWP 的 `ApplicationFrameWindow` 可以 `SetWindowPos`，但内部内容由系统托管，某些状态（全屏/平板模式）下会被拒绝；Chrome/Electron 的无边框窗口 `GetWindowRect` 与视觉边界有 7–8px 阴影差。

### 3.5 抓取模式（矩形 / 套索）

**覆盖层**：
- 覆盖整个虚拟屏幕：`GetSystemMetrics(SM_XVIRTUALSCREEN / SM_YVIRTUALSCREEN / SM_CXVIRTUALSCREEN / SM_CYVIRTUALSCREEN)`，窗口样式 `WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_TOPMOST`，半透明黑底（10%–20%）+ 自绘选框。
- **不抢焦点**：`WS_EX_NOACTIVATE` 阻止点击激活；**不要**在鼠标按下时 `SetForegroundWindow` 自己；`Esc` 用 `GetAsyncKeyState` 或覆盖层内的键盘消息处理（覆盖层不激活时收不到键盘，所以用 `RegisterHotKey` 注册 Esc 更稳）。
- **不阻塞目标窗口**：抓取期间覆盖层本来就该吃掉鼠标（这是设计），但不要 `SetCapture` 后永久不释放；退出时确保 `ReleaseCapture`。

**命中判定（覆盖层自己会挡住 `WindowFromPoint`，让它返回自己）**：

| 方案 | 做法 | 评价 |
|------|------|------|
| A. z-order + 矩形求交（推荐） | `EnumWindows` 顺序即 z-order，过滤 cloaked/工具窗后，用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`（值 9）取视觉边界，与选框求交 | 确定性高、无副作用、可解释；阴影/圆角误差约几像素 |
| B. `WindowFromPoint` 取样 | 临时给覆盖层加 `WS_EX_TRANSPARENT` 让点击穿透，再对采样点调用 `WindowFromPoint` | 会丢鼠标事件；文档明确它**不返回隐藏或禁用窗口**；对分层窗口行为不稳定 → 不推荐做主路径 |
| C. 逐像素/缩略图命中 | `PrintWindow` / `DwmRegisterThumbnail` 取像素做掩码 | 慢（每帧数十 ms），GPU 加速窗口取不到内容，套索边缘还涉及 alpha 判定 → **明确不做** |

**判定规则建议**：
- 矩形框选：窗口矩形与选框的**交集面积 ≥ 窗口面积 50%**，或「窗口中心点在选框内」；两者取并集可配置。**不要「碰到就算」**，否则一个最大化窗口会被任何小选框选中。
- 套索：多边形，判定「窗口中心点在多边形内」为主，可选「相交面积 ≥ 60%」。套索本质是自由形状，用中心点判定最符合直觉，也最便宜（`PointInPolygon` 是纯数学）。
- 实时高亮：**在覆盖层上画边框**，不要给目标窗口加 `WS_EX_LAYERED` 或改 DWM 属性（会和 WindowTinter 直接抢状态）。

### 3.6 释放回原位

需要记录的最小快照：

```
WindowSnapshot {
  hwnd, pid, processStartTime, appKey
  showCmd                     // 来自 WINDOWPLACEMENT，区分 normal/maximized
  rcNormalPosition            // WINDOWPLACEMENT，工作区坐标（最大化窗口必须用这个）
  visualRect                  // DWMWA_EXTENDED_FRAME_BOUNDS，物理屏幕像素
  monitorDeviceName           // EnumDisplayDevices / GetMonitorInfo
  dpi                         // GetDpiForWindow
  zPrevHwnd                   // GetWindow(hwnd, GW_HWNDPREV)，可选
}
```

边界情况：

| 情况 | 处理 |
|------|------|
| 窗口已被关闭 | `IsWindow(hwnd)` 为 false → 跳过，并标记该组成员失效（可选：按 appKey 重启） |
| 进程重启、HWND 变化 | HWND 不可复用，只能按 `appKey` 重新匹配；**MVP 只做会话内还原**，重启恢复放 P1 |
| 窗口已被用户移动 | 仍按快照还原（这是「释放回原位」的语义）；提供「仅还原到当前显示器」的宽松模式 |
| 最大化窗口 | 用 `rcNormalPosition`，不是 `GetWindowRect`；还原时先 `ShowWindow(SW_RESTORE)` 再摆放 |
| 分辨率/缩放变化 | 按「旧 DPI / 新 DPI」比例缩放矩形，再 clamp 到当前显示器工作区（`GetMonitorInfo().rcWork`） |
| 显示器被拔掉 | `monitorDeviceName` 找不到 → 落到主屏工作区并居中 |
| 还原后又想恢复原层级 | 不要强行改 z-order（会干扰用户当前工作）；只在需要激活时 `SetWindowPos(HWND_TOP, SWP_NOACTIVATE)` |

### 3.7 全局快捷键

- `RegisterHotKey(消息窗口, id, MOD_CONTROL|MOD_ALT|MOD_NOREPEAT, VK)`；失败时 `GetLastError()` 通常为 `ERROR_HOTKEY_ALREADY_REGISTERED (1409)`，可据此做**冲突提示**。
- 文档明确：**含 Win 键的组合保留给系统**；`F12` 永久保留给调试器；同一 `(hWnd, id)` 重复注册会并存，必须显式 `UnregisterHotKey`。
- 建议默认键位：`Ctrl+Alt+1..9`（单窗口）、`Ctrl+Alt+G`（抓取成组）、`Ctrl+Alt+Shift+1..5`（组调取）。避开 `Alt+Space`（PowerToys Run / CmdPal 常用）、`Win+Shift+\``（FancyZones 编辑器）、`Ctrl+Alt+P/T`（WindowTabs 命令面板/搜索）。
- 不要用低级键盘钩子做热键：会被 UIPI、输入法、游戏反作弊干扰，且需要常驻高权限。

### 3.8 多显示器、混合 DPI、高刷新率

- 清单文件声明 **PerMonitorV2**（`dpiAwareness = PerMonitorV2`），否则 WPF 会被系统位图拉伸，坐标全错。
- 坐标统一用**物理像素**存取（`SetWindowPos`、`GetWindowRect`、`DWMWA_EXTENDED_FRAME_BOUNDS` 都是物理像素）；只在 WPF 绘制时转 DIP。
- DPI 查询用 `GetDpiForWindow`（Win10 1607+），**不要用 `GetDpiForMonitor`**：文档说明它在 per-monitor DPI 感知线程中不可靠。
- 跨屏移动窗口会收到 `WM_DPICHANGED`，系统会「建议」新矩形；跟随它，否则窗口内容会错位。
- 高刷新率没有专门 API：动画交给 DWM 合成（WPF 的合成线程），**不要自建固定 60fps 的 `DispatcherTimer`**；多屏不同刷新率时以合成时钟为准。

### 3.9 权限与限制

| 场景 | 结论 | 原因 |
|------|------|------|
| 操作提权（管理员）窗口 | **受限** | UIPI 阻止低完整性进程向高完整性窗口发送窗口消息，移动/激活/还原普遍失败或静默无效。只能「以相同权限运行」，即 Dock 也提权——但那样会失去 Explorer 拖放（见 3.2） |
| 受保护进程（PPL）、部分安全软件 | **不可做** | 系统级保护，任何外部操作都被拒绝；直接跳过 |
| 全屏独占游戏 | **不支持** | 独占全屏绕过 DWM 合成，覆盖层和 topmost 都不可见；反作弊还可能拦截覆盖层。产品明确声明不支持 |
| 锁屏 / UAC 安全桌面 | **不可做** | 独立桌面，普通进程不可见；不要尝试 |

**结论：默认非提权运行；设置里提供「以管理员重启」开关并明确提示代价（拖放失效、UAC 弹窗）。**

## 4. 技术选型

| 方案 | 部署体积 | 冷启动 | 自绘/透明/动画 | Win32 互操作 | 结论 |
|------|----------|--------|----------------|--------------|------|
| **C# .NET 8 + WPF** | 框架依赖约 10–15 MB；自包含（含 R2R）约 60–80 MB | 约 0.3–0.8 s（ReadyToRun + 常驻托盘，实际只在开机启动一次） | `AllowsTransparency`（`WS_EX_LAYERED`）可做逐像素透明；Storyboard 动画走 DWM 合成；圆角/阴影成熟 | P/Invoke 成本低；OLE 拖放、`SetWinEventHook`、COM（`IShellLink`、`IVirtualDesktopManager`）都有现成封装 | **推荐** |
| WinUI 3 | 依赖 Windows App SDK 运行时（未打包需随应用分发，通常 +几十 MB） | 明显慢于 WPF | 现代控件与云母背景好看，但**任意形状/逐像素透明窗口要回退 Win32**，Dock 这种异形窗口反而更难 | 可用，但要 `AppWindow`/`HwndSource` 混合 | 不推荐（除非要 Win11 原生观感优先） |
| WinForms | 最小（框架依赖约 10 MB） | 最快 | 动画/圆角/模糊/高 DPI 自绘需要大量 GDI+ 手写，效果差 | 最直接 | 只适合极简 Dock，不推荐 |
| C++ / Win32 + Direct2D / DirectComposition | < 5 MB | 毫秒级 | 完全可控，可做最顺的 120Hz 动画 | 原生 | 仅当「体积 < 5MB 且毫秒级启动」是硬指标时选；托盘/设置/JSON/更新全要自写，工期翻倍 |

**结论**：用 **C# / .NET 8 + WPF**，Win32 只作为 P/Invoke 层。理由：
1. 本项目 90% 的复杂度在 **Win32 窗口操作**，不在 UI 框架；WPF 的 `HwndSource`/`WindowInteropHelper` 让两者结合最省事。
2. WPF 的 `AllowsTransparency` + Storyboard 足以做 Dock 的缩放/滑入动画；Dock 窗口尺寸小，分层窗口的合成开销可接受（**不要做全屏常驻的透明窗口**）。
3. 托盘、设置页、JSON 持久化、单文件分发都有成熟方案；启动慢的问题可以用「开机静默启动 + 常驻」规避——用户感知的是**唤出延迟**，而唤出只是 `ShowWindow`，与框架无关。
4. 注意：WPF **不支持 NativeAOT**（截至 .NET 9），裁剪（trimming）对 WPF 支持不完整；只开 ReadyToRun 即可。

> 如果后续要压体积，最有效的不是换框架，而是：去掉设计器资源、压缩图标、`PublishSingleFile + ReadyToRun`，通常能落在 30–40 MB（自包含）。

## 5. 架构草图

```
┌────────────────────────────── Dock.exe (单进程, 非提权, PerMonitorV2) ──────────────────────────────┐
│                                                                                                   │
│  App Shell                                                                                        │
│  ├─ TrayService            托盘图标 / 开机自启 / 单实例(mutex)                                      │
│  ├─ HotkeyService          RegisterHotKey + 消息窗口 + 冲突检测                                     │
│  └─ SettingsService        JSON 配置（不含业务窗口数据）                                             │
│                                                                                                   │
│  Core (纯逻辑, 无 UI 依赖, 可单测)                                                                  │
│  ├─ WindowInventory        EnumWindows 全量扫描 + SetWinEventHook 增量 + 节流 + 过滤规则              │
│  ├─ WindowIdentity         AppKey(exe/AUMID) / InstanceKey(hwnd+pid+启动时间) / UWP 下钻              │
│  ├─ DockModel              Pin(程序) / Group(组) / Layout(布局方案) / 排序                            │
│  ├─ SnapshotService        WINDOWPLACEMENT + EXTENDED_FRAME_BOUNDS + monitor + dpi                  │
│  ├─ PlacementService       SetWindowPos / DeferWindowPos / 跨 DPI 换算 / 工作区 clamp                 │
│  └─ RestoreService         失效检测 → 还原 → 激活（含降级策略）                                       │
│                                                                                                   │
│  UI (WPF)                                                                                         │
│  ├─ DockWindow             WS_EX_TOPMOST|TOOLWINDOW|NOACTIVATE, 自动隐藏, 拖放目标(IDropTarget)       │
│  ├─ ItemView               图标 / 运行指示 / 悬停预览(DwmRegisterThumbnail, P2) / 组徽标               │
│  ├─ CaptureOverlay         全屏分层窗口, 矩形/套索绘制, 实时高亮                                      │
│  └─ GroupPanel             组的成员管理、布局预设、恢复入口                                           │
│                                                                                                   │
│  Interop                    P/Invoke + COM(IShellLink / IVirtualDesktopManager)                     │
└───────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**线程模型（关键）**
- 所有 **Win32 窗口操作**（`SetWindowPos`、`ShowWindow`、`SetForegroundWindow`）都在 **UI 线程**执行，避免跨线程 `SetWindowPos` 的同步问题。
- `SetWinEventHook` 回调在系统线程，只做「打标记 + 投递」，用 `Dispatcher.BeginInvoke` 以 100ms 合并。
- `IVirtualDesktopManager` 是 COM，需在 STA 线程创建并缓存，不要每次调用都 `CoCreateInstance`。
- 全量扫描（每 2s）与增量事件共用同一份索引，UI 只读快照。

**核心数据模型**

```jsonc
{
  "version": 1,
  "pins":  [{ "appKey": "C:\\...\\Code.exe", "displayName": "VS Code", "order": 0 }],
  "groups": [{
    "id": "g1", "name": "写作",
    "hotkey": "Ctrl+Alt+Shift+1",
    "layout": "restore-original",          // 或 "preset:left-right"
    "members": [{
      "appKey": "C:\\...\\chrome.exe",
      "titleHint": "文档 - Chrome",          // 仅用于重启后匹配，不作主键
      "showCmd": 1,
      "rcNormal": [100, 80, 1100, 900],      // 工作区坐标
      "visualRect": [92, 72, 1116, 916],     // 物理屏幕像素
      "monitor": "\\\\.\\DISPLAY2",
      "dpi": 144
    }]
  }]
}
```

**两条主要流程**

```
抓取:  Hotkey(G) → 创建覆盖层 → 鼠标拖拽(矩形/套索)
        → 每个 mouseup: EnumWindows(z-order) 过滤 → 与选区求交 → 高亮
        → 结束: 生成 Group + 对每个成员 Snapshot → 覆盖层销毁 → Dock 显示组徽标

还原:  Hotkey(组) / 点击组 → 逐个 IsWindow 校验 → 失效成员剔除
        → ShowWindow(SW_RESTORE) → BeginDeferWindowPos 批量定位
        → EndDeferWindowPos → SetForegroundWindow(主窗口) → 失败则 FlashWindowEx
```

## 6. MVP 与阶段计划

### P0：核心闭环（第一版只做这些）

| 做 | 说明 |
|----|------|
| 托盘常驻 + 单实例 | mutex 防多开；开机启动可选 |
| 悬浮 Dock | 单屏、贴左/右边缘、自动隐藏、置顶、无边框圆角 |
| 拖入 | 资源管理器拖 `.lnk`/`.exe`；右键/热键「加入当前前台窗口」 |
| 点击 Dock 项 | 未运行 → 启动；运行 → 激活最近窗口（含最小化还原） |
| 单窗口热键 | `Ctrl+Alt+1..9`，可改键 |
| 抓取成组（**矩形**） | 覆盖层 + z-order 命中 + 实时高亮 |
| 组调取 | 热键/点击 → 按快照批量摆回原位 |
| 会话内数据 | 内存模型 + 退出时写 JSON（重启恢复放到 P1） |

**P0 明确不做**：套索、跨虚拟桌面切换、UWP 深度适配、缩略图预览、组持久化重启恢复、多屏混合 DPI 的完美换算（先按主屏 + clamp 处理）、模拟标题栏拖动、提权。

### P1：可用性补齐
- **套索选择**（多边形 + 中心点判定）
- **组持久化与重启恢复**：按 `appKey` 重新匹配；未运行的应用可选「启动后摆放」
- **多显示器 / 混合 DPI**：按 `monitor + dpi` 缩放与 clamp
- **布局预设**：左右分屏、2×2、三栏，组的「原始位置 / 预设」双模式
- **排除规则**：按进程名/标题排除（输入法、系统窗、游戏）
- **热键冲突检测**与一键改键

### P2：打磨与扩展
- 跨虚拟桌面：只做 `MoveWindowToDesktop`（需目标 GUID，能力有限），不做切换
- DWM 缩略图悬停预览（`DwmRegisterThumbnail` / `DwmUpdateThumbnailProperties`）
- 拖拽排序、磁吸分区、组内窗口图标堆叠
- CmdPal 扩展入口（把「调用组」暴露成命令，避免自己抢 `Alt+Space`）
- 导入/导出配置、便携模式

## 7. 风险清单与最小探针

> 每个探针都是独立的小程序/控制台工具，**不需要现在实现**，用来在写产品代码前把假设打掉。

| # | 风险 | 为什么会翻车 | 最小探针 | 通过标准 |
|---|------|--------------|----------|----------|
| 1 | **前台激活失败** | `SetForegroundWindow` 受前台锁限制，热键触发时本进程通常不是前台进程，可能只闪任务栏 | 控制台程序注册 `Ctrl+Alt+9`，对记事本连续调用 100 次「Restore + SetForegroundWindow」，记录返回值；再测 `AttachThreadInput` 兜底 | 兜底方案成功率 ≥ 95%，且失败时能明确走 `FlashWindowEx` 提示 |
| 2 | **覆盖层抢焦点 / 吞输入** | 点击覆盖层可能激活它，导致目标窗口失去焦点、`Esc` 收不到 | 创建 `WS_EX_NOACTIVATE` 全屏分层窗口，点击后检查 `GetForegroundWindow()` 是否变化；检查目标窗口 hover 是否仍工作 | 前台窗口不变；`Esc` 可退出；退出后鼠标无残留 capture |
| 3 | **命中判定与视觉不一致** | 阴影、圆角、无边框窗口导致 `GetWindowRect` 比视觉大 7–8px；最大化窗口误差更大 | 对 10 个应用（记事本、Chrome、VS Code、Explorer、UWP 设置、微信…）同时打印 `GetWindowRect` 与 `EXTENDED_FRAME_BOUNDS` | 差值可量化（预期 0–16px）；用视觉边界后，矩形框选误选率 0 |
| 4 | **混合 DPI 位置漂移** | 100% + 150% 双屏下，物理/DIP 混用会导致每轮还原偏移累积 | 双屏环境，对同一窗口「快照 → 移走 → 还原」20 次，记录每次偏差 | 20 次后累计偏移 ≤ 4px；跨屏还原不越界 |
| 5 | **与 FancyZones / Groupy / WindowTinter 冲突** | 低级钩子叠加、双重成组移动、置顶层级争夺、热键抢占 | 开启 FancyZones 后：程序化 `SetWindowPos` 与模拟拖动各测一次，观察是否被吸附；注册候选热键看是否 `1409` | 程序化移动不被吸附；热键冲突能被检测并提示；不改目标窗口 exstyle |
| 6 | **提权窗口不可控** | UIPI 拦截，API 静默失败或返回拒绝 | 普通权限进程操作管理员权限的记事本：移动、还原、激活各 10 次，记录返回值和 `GetLastError` | 不崩溃、不卡死；UI 明确标记「该窗口需要管理员权限」 |

**最可能翻车的前三名**：1（前台激活）> 3（命中判定）> 4（混合 DPI）。这三项建议**先做探针再写产品代码**。

## 8. 与现有工具的关系

| 工具 | 重叠点 | 共存注意事项 |
|------|--------|--------------|
| **PowerToys / FancyZones** | 都移动窗口、都关心布局 | FancyZones 在**用户拖动标题栏**时接管吸附；我们只用程序化 `SetWindowPos`，不会触发它。**绝对不要**用 `SendMessage(WM_NCLBUTTONDOWN, HTCAPTION)` 模拟拖动，否则会被 FancyZones 吸进分区。FancyZones 编辑器默认热键 `Win+Shift+\``，不要占用。若用户在 FancyZones 里开了「覆盖系统贴靠」，我们摆放的矩形不受影响，但用户手动整理组内窗口会被吸附——写进帮助文档 |
| **PowerToys / Always on Top** | 都改窗口层级 | 被 PowerToys 钉为 topmost 的窗口，我们**不要**试图把它拉回普通层（不要改 `HWND_NOTOPMOST`），只在当前 band 内摆位置；Dock 自身保持 topmost，但不要跟它抢 |
| **CmdPal（Command Palette）** | 全局唤出、快速启动 | 默认唤出键通常是 `Alt+Space`（可在设置改），**不要注册同一个键**。P2 可做 CmdPal 扩展把「调取组」暴露成命令，比自建全局唤出更符合用户习惯 |
| **WindowTinter（自研）** | 都会读写窗口的视觉状态 | 它大概率改 DWM 合成属性（如 `SetWindowCompositionAttribute`）或扩展样式。**本项目不碰目标窗口的任何视觉属性**：不加 `WS_EX_LAYERED`、不改 DWM attribute、不注入进程；抓取高亮只画在自己的覆盖层上 → 理论上零冲突。双方若都用 `SetWinEventHook`，务必 `WINEVENT_SKIPOWNPROCESS` 并做事件去重 |
| **Groupy 2 / WindowTabs / AquaSnap** | 都会「成组移动」窗口 | 同时启用会出现**双重位移补偿**（两边都在跟 `EVENT_SYSTEM_MOVESIZEEND` 后重排）。检测到这些进程在运行就提示「请关闭其组移动功能」，或只在用户显式点击「调取组」时移动，不做实时联动 |
| **Windows Snap / Snap Groups** | 都成组恢复 | 系统 Snap Group 是自动生成的，无法被第三方创建或修改；我们的组是独立概念，不要试图「合并」到系统组。摆放成贴靠矩形不会让系统认为它们是 Snap Group |

## 9. 一句话结论（复述）

**这个工具值得做，但价值不在「Dock」，在「窗口工作台」。**

- 差异化只有三点：**容器式侧栏**、**框选/套索成组**、**一键原位还原**。三者缺一，就会退化成「又一个 MyDockFinder / 又一个 Groupy」，没有做的必要。
- 最小代价落地：**C#/.NET 8 + WPF 单 exe，非提权、不注入、不改目标窗口样式**；P0 只做「拖入 + 单击调取 + 单窗口热键 + 矩形抓取 + 原位还原」。
- 先做三个探针（前台激活、命中判定、混合 DPI），再决定是否投入 P1。三个探针里任何一个不达标，都应缩小范围（例如放弃套索、只做单屏、只做「移到当前桌面」）。
